# 程序节点重整 —— 设计稿

> 状态：**设计已记录，尚未实现**
> 记于 2026-09-30。用户口述的设计 + 实现前的技术分析。

---

## 0. 总纲：端点是第一公民

每个程序节点的输入 / 输出端点都有自己的：

| 属性 | 说明 |
|---|---|
| **ID** | **纯数字**，节点内唯一。可以编辑，但不允许重复 |
| **标签** | 只在**悬停**和**选中**时显示。多选时同样显示 |

**原则上，一个输入端点对应节点的一个"空"** —— 也就是节点上可供填写的一格。
节点种类多，这套对应关系要慢慢设计，不一次定死。

---

## 1. 变量节点 / 广播节点

- **变量节点**：「全局 / 局内」的分类**保持不变**（原计划取消，已确认保留）
- **一个变量节点可以设置多个变量** —— 每个变量**各占一格**
- **新增广播节点**：
  - 把输入值变成**全局变量**
  - 和变量节点长得一样，但**只能设置变量名**
  - 另一边显示**实际输出**（解析后的值）

---

## 2. 运算符节点（替换「运算节点」）

- **删除**原来的运算节点
- 新的运算符节点**只是运算符**，不再带"运算值"那个格子
- 自带 **2 个输入端点 + 1 个输出端点**
- **两个输入端点分别对应「加减乘除的两个数」** —— 也就是节点上两个操作数格子。
  端点接上了就用接进来的值，没接就用格子里填的值
- 输出值 = 所有输入值按节点运算符**依次运算**的结果
- 运算顺序 = **按端点 ID 升序**

---

## 3. 循环节点（新增）

- 两个输入 **A / B**，一个输出
- 自定义参数 **N**：不小于 0 的整数（自动取整）
- 输出 = 把 **A 到 B 之间的阶段运算**重复 N 次

**「A 到 B 之间的阶段」的含义（已确认）**：

A、B 是**两个节点**。**A → B 之间的那条子图就是循环体**，整条子图跑 N 次。
输出是循环体跑完之后的结果。

---

## 4. 条件节点（替换「通路节点」）

- **取消**通路节点
- 条件节点：**一个输入，一个输出**
- 输入为 **1** 时，输出**所填的值**
- 输入不为 1 时 —— 按"逻辑不通"处理（下游取不到值）

---

## 5. ⚠ 实现前的障碍：现在的求值模型撑不住多输入

这是动手前必须解决的核心问题。

### 现在的模型：**路径步进**

`evalFromIn(ctx, def, start, inside, targetId)` 是从变量定义节点出发的一次 BFS
（`src/core/vars.js:383`）。它沿着边走，**每个节点都是一个「一进一出」的变换**：

```js
const out = (m && isOpNode(m)) ? applyOperator(cur.v, m.opDef) : cur.v;
```

每条路径各带各的累加值（这个是刻意做的，早先共用累加器导致分支互相污染，修过）。

### 为什么撑不住

运算符节点要 **2 个输入**、循环节点要 **A/B 两个输入**。而"路径步进"到这类节点时，
手里**只有一条**路径的值 —— 另一条还没走到。

这不是加个字段能解决的，是模型本身的问题。

### 建议：改成「拓扑求值 + 汇合」

```
1. 从目标节点反向收集所有依赖到的最小闭包
2. 拓扑排序（用 idx.parent 那套，或者现算一次）
3. 按序求每个节点的值：
     变量节点  -> 自己的值（值本身可能引用别的变量，沿用现有插值）
     运算符节点 -> fold(运算, [每个输入边带来的值])
     条件节点  -> 输入为 1 ? 填的值 : BLOCKED
     循环节点  -> 见第 3 节的读法
4. 记忆化：一个节点在一个 Ctx 里只算一次
```

这套模型还有个附带好处：**循环节点、跨层引用本来就该这么算**，
现在的路径步进是为"链式变换"临时凑的。

### 必须一起解决的三件事

| 问题 | 说明 |
|---|---|
| **环** | 拓扑排序遇到环要有明确行为。现在是 `seen` 集合天然挡住的。建议：环上的节点值取 `[循环]`，不崩 |
| **被通路挡住的边** | `VAR_BLOCKED` 语义要保留：够不着 ≠ 被挡住 |
| **性能** | 现在每次 `reindex` 全量求值。拓扑 + 记忆化实际上更快（不再重复走路径） |

### 迁移风险

`evalFromIn` 被这些地方依赖，改的时候要一起过：

- [ ] `resolveVarIn` —— `{name}` 取值的入口
- [ ] `defValueIn` —— 变量定义自己的值
- [ ] `functionResultIn` —— 程序组（原函数分组）的输出
- [ ] `outputValueIn` —— 输出节点的值
- [ ] `evalFromIn` 里 `cur.v` 的传递（每条路径各带各的）
- [ ] 嵌入文档的 `embedCtxCache`（跨层引用）

现有断言里 **J / K / VV / GX / SC 几组** 大量覆盖这套语义，改完必须全绿。

## 6. 已确认的设计决定

| # | 问题 | 决定 |
|---|---|---|
| 1 | 循环节点「A 到 B 之间的阶段运算」 | **A、B 是两个节点，A→B 之间的子图就是循环体**，整条子图跑 N 次 |
| 2 | 变量节点取消作用域后怎么引用 | **不取消** —— 全局 / 局内的分类**保持不变**，广播节点照常新增 |
| 3 | 运算符节点两个输入的运算顺序 | **按端点 ID 升序** |
| 4 | 输入端点对应节点上的哪一格 | **对应加减乘除的两个数**（两个操作数格子各对一个输入端点） |
| 5 | 一个变量节点多个变量，值怎么给 | **每个变量各占一格的框** |
| 6 | 老存档里的运算节点 / 通路节点 | **就地转换**（读档时转成新种类，别让老文档打不开） |

### 由答复推出的两条新要求

**① 端点 ID 必须可排序，而且是求值顺序的依据。**

所以 ID 不能只是「不重复的数字」，还得是**正整数、建议连续**。
UI 上要能看出顺序（按 ID 排好显示），改 ID 之后**求值顺序跟着变** —— 这是有意的。

**② 循环节点是第一个真正需要「子图」概念的节点。**

A→B 之间的子图要能被识别和求值：

```
1. 找出 A、B 两个输入端点各自连到哪条上游
2. 把 A 到 B 之间的节点集合圈出来（沿边可达，且不越过 B）
3. 每次迭代：把这个子图当成一条求值链跑一遍
4. 迭代 N 次，输出最后一次的结果
```

**这和拓扑求值模型是同一套东西** —— 子图就是拓扑序里的一个区间。
所以第 5 节的 A 期（换模型）是循环节点的**前置条件**，不是可选项。

### 就地转换的具体规则（第 6 条）

| 老 | 新 | 转法 |
|---|---|---|
| 运算节点 `opDef:{op, operand}` | 运算符节点 | 第 1 格接输入，第 2 格填原来的 `operand` |
| 通路节点 `control:'switch'` | 条件节点 | `on:true` → 条件值填 `1`；`on:false` → 留空（永远不通） |

转换写在 `normalizeVarDef` / `normalizeOpDef` 这一层，**读档时自动发生**，
用户不用做任何事。

## 7. 建议的实施顺序

每一期都能单独发、单独验证：

| 期 | 内容 | 为什么这个顺序 |
|---|---|---|
| **A** | **求值模型换成拓扑 + 汇合**，但**先不加新节点** | 纯重构，行为不变，靠现有 1499 条断言兜底。这一步做不干净，后面全是坑 |
| **B** | 端点模型：数字 ID + 标签 + 悬停/选中显示 + 唯一性校验 | 新节点都依赖它 |
| **C** | 运算符节点（替换运算节点）+ 条件节点（替换通路节点） | 最简单的两个，先验证 A/B |
| **D** | 广播节点 + 变量节点多变量 + 取消作用域 | 牵动插值，放后面 |
| **E** | 循环节点 | 最复杂，等 A 稳了再说 |

> **A 期不做就等于在流沙上盖楼。** 运算符节点的多输入和循环节点都要求汇合语义，
> 而现在的路径步进给不了。

## D 期剩余：一个变量节点多个变量（未做）

### 为什么不能"顺手加一下"

`defValueIn(ctx, def)` 里的 `def` **现在就是一个节点**。一个节点只有一个变量时这没问题；
一个节点有多个变量时，「这个 `{名字}` 指的是哪一个」就说不清了。

所以核心是把 `def` 从「节点」升级成「节点 + 下标」。这会一路牵动：

| 函数 | 现在 | 要变成 |
|---|---|---|
| `findVarDefIn` | 返回节点 | 返回 `{ node, index }` |
| `varVisibleIn` | 用 `def.id` | 用 `(def.node \|\| def).id` |
| `defValueIn` | 读 `def.varDef` | 按 index 读 `def.node.varDefs[index]` |
| `evalFromIn` | 用 `def.id` 当起点 | 同上 |
| `refAnchorOf` | 节点本身就够了 | 同上 |

### 建议的兼容策略（关键）

**保留 `varDef` 作为第 0 个变量**，新增可选的 `varDefs`：

```js
node.varDef              // 第 0 个（老存档、老代码全都靠它）
node.varDefs             // 可选；存在时 [0] 必须和 varDef 一致
```

于是 `def` 可以是**一个节点**（= 第 0 个变量）或者 `{node, index}`。
所有老调用点一行都不用改，新代码用带下标的形状。

### 还有几处要一起改

- `varLayout` / `sizeVarNode` / `drawVarNode`：N 行，每行「名字格 + 值格」
- `hitVarPart`：返回 `varName0` / `varValue1` 这种带下标的
- `editing.js` 的 `editValue` / `editSetValue`：认下标
- `refreshVarText`：每个变量各自插值
- 三种控件（勾选 / 滑条 / 条件）算第几个变量？**建议：控件只管第 0 个**，其余是普通变量
- `serialize` / `deserialize`：加 `varDefs`，老存档读进来只有 `varDef`

### 该有的断言

- 一个节点两个变量，各自能被子节点引用到，互不串
- 老存档（只有 `varDef`）读进来 = 一个变量，行为不变
- 同名变量跨节点时，优先级仍然决定谁赢
- 第 1 个变量上的插值用**这个节点**当锚点（作用域规则和以前一致）
- 存读往返
- 三种控件仍然只作用在第 0 个变量上

### 为什么这轮不做

它牵动约 100 条现有断言（J / K / VV / GX / SC 几组都是求值语义的主力），
而 `def` 的形状一改就是全线影响 —— **塞在尾巴上做会把变量系统弄坏**。
单独一轮，先把 `def` 的双形状铺开、跑绿，再加 UI。

## 待办（用户提出，尚未动）

### 1. 输入 / 输出端点的标准化

现在端点是「每个节点各自一套」：程序节点有端点表、普通/图片/表格节点走老的边中点、
分组又是一套四向锚点。三套并存，是这一路 bug 不断的根源
（`hitPort` / `anchorsFor` / 边落点各修过一次，每次都是"某个消费点还在用老约定"）。

要做的是：**一套端点模型管所有东西**，分组也纳入进来，老的边中点彻底退役。
`docs/ports-design.md` 是端点方案的正本。

### 2. 用链接引用本地 / 网络的文件 / 数据

节点的值可以来自一个**外部来源**，而不是只能手填或从上游连过来：

- 本地文件（配合素材库那套 `Store`：native / fs / idb / mem 四个后端）
- 网络地址（`fetch` 拿 JSON / 文本）

设计上要注意的：

- **同步 vs 异步**：现在的求值是**同步**的（`evalFromIn` / `valueFromUpstream` 一路同步）。
  网络取值是异步的，得先把值**拉进缓存**（像 `embedCtxCache` 那样），
  求值时只读缓存 —— 不能让求值链变成 async，那会牵动所有调用点
- **失败与超时**：拿不到就退回 `无` / `[未定义]`，不能崩
- **安全**：跨域、以及别把整个页面卡住
- **素材库已经在管文件了**，这条更像是「给素材库加一个"以变量形式引用"的入口」

### 3. 「程序化节点」→「外观节点」，并彻底参数化

现在的外观算符是**枚举**的：`op` ∈ {style, shape, move, value}，参数只有 `key` + `value`。
要改成**参数直接填**：

| 参数 | 例子 |
|---|---|
| 形状 | `shape = 菱形` |
| 偏移量 | `dx = {间距}` |
| 倒角 | `radius = 8` |
| 颜色 | `color = #ff8fb1` |

- 每个参数**可以填字面量，也可以引用变量**（`{间距}`）—— 这条已经有基础了
  （`resolveProgramValue` 就是干这个的），要扩到所有参数
- 顺带把节点名从「程序化节点」改成「外观节点」
