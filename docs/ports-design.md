# 自定义输入 / 输出端点 —— 设计方案

> 状态：**方案已定，尚未实现**
> 记于 2026-09-30。要做的时候从这份开始，不用重新推一遍。

---

## 1. 要解决什么

现在每个节点的端点都是**固定的四向**：上 / 下 / 左 / 右各一个，位置固定在中点。

- 程序节点只能从四个固定位置进出
- 程序组（原函数分组）的输出**只有组内那一个输出节点**，想要多个输出就得拆成多个组

要做的：

1. **程序节点可以自定义输入 / 输出端点** —— 数量、位置、名字都自己定
2. **程序组可以自定义选择输出变量和输出端点** —— 一个组吐出多个值，各走各的边

---

## 2. 现状（动手前先确认这些还在）

| 东西 | 在哪 |
|---|---|
| 四向端点的坐标 | `portPos` / `portAt`（`src/view/*`） |
| 端点命中 | `hitPort`（`src/view/hit.js`） |
| 从端点拉线 | `pointer.js` 的 `drag.mode === 'link'` |
| 拖端点改接 | `relink`（`pointer.js`） |
| 边的起止锚点 | `edge.s` / `edge.t`，锚点选择走「自动锚点」+ 右键钉死 |
| 分组端点 | 分组也有四向端点，`U06` 有断言 |
| 跨层引用 | `{嵌入节点名.输出名}` —— **已经有一套了**，见 `vars.js` 的 `refAnchorOf` |
| 函数分组取值 | `functionResult()` —— 找组内那个输出节点 |

**关键**：跨层引用的解析路径已经存在。端点方案应该**复用**它，而不是新造一套。

## 3. 数据模型

```js
// 节点上的端点表。
// ★ 没有这个字段 = 用默认的四向端点 —— 老存档零改动，这是硬要求。
node.ports = {
  ins:  [ { id:'in1',  label:'输入', side:'l', at:0.5 } ],
  outs: [ { id:'out1', label:'求和', side:'r', at:0.25 },
          { id:'out2', label:'均值', side:'r', at:0.75 } ]
};

// side: 't' | 'b' | 'l' | 'r'   在哪条边上
// at:   0..1                     沿那条边的位置（0 = 起点，1 = 终点）
// id:   稳定标识，边靠它认端点

// 边也记一下是从哪个端点走的
edge.sPort = 'out2';   // 出发端点（没有 = 默认）
edge.tPort = 'in1';    // 进入端点（没有 = 默认）
```

### 为什么用 `at` 而不是像素坐标

端点必须**跟着节点走**。用「哪条边 + 边上的比例」，节点缩放 / 改尺寸 / 移动时端点自动跟着，不需要任何同步代码。像素坐标就得在每个改动节点尺寸的地方都补一次 —— 那种「每个地方都要记得」的写法在这个项目里已经翻过几次车了。

### 为什么 id 要和 label 分开

`label` 是给人看的，随时能改；`id` 是给边认的。用 label 当标识的话，改个名字就把所有边弄断了。

## 4. 渲染 / 命中 / 连线

新增一个**唯一入口**，所有地方都从这里拿端点：

```js
/* 返回这个节点实际生效的端点表。没配 ports 就是默认四向。 */
function portList(n){
  // 输入：ports.ins，缺省 -> [{ id:'def-t', side:'t' }, { id:'def-b', side:'b' }, ...]
  // 输出：ports.outs，缺省 -> 同上
  // 返回 { ins:[...], outs:[...] }
}
```

然后：

| 原来 | 改成 |
|---|---|
| `portPos(n, side)` | `portPos(n, port)` —— port 是端点对象 |
| `hitPort(p)` | 遍历 `portList(n)` 里所有端点，取最近的 |
| 拉线时的起点 | `drag.from = { node, port }` |
| 边的坐标 | 按 `e.sPort` / `e.tPort` 反查端点 |

**端点画成小圆点**，`label` 非空时在旁边画短标签。悬停时端点放大 —— 现在悬停已经有个 `hover` 状态了，接上去。

---

## 5. 程序组的输出端点

程序组本来就是「一个分组 + 组内的输出节点」。自定义输出 = **组上挂一张端点表，每个输出端点绑定到组内一个节点**：

```js
group.ports = { outs:[ { id:'o1', label:'折后价', bind:'<组内变量节点 id>' } ] };
```

取值规则：

| 情况 | 值 |
|---|---|
| 组没有 `ports` | 老行为：组内那个输出节点的值（`functionResult()`） |
| 组配了 `ports` | 每个端点各取它 `bind` 指向的那个组内变量的值 |

`bind` 存**节点 id**。节点被删掉时，那个端点变成「没绑定」—— 取值给 `[未定义]`，但不崩，也不删端点（用户可能只是临时删了，撤销回来就该好）。

---

## 6. 引用语法

**复用现有的跨层引用**，不新增语法：

```
{折扣函数.折后价}
```

`{嵌入节点名.输出名}` 已经在跑了，解析路径在 `vars.js`。端点方案只是让「输出名」多几种可能。

## 7. UI

| 在哪 | 做什么 |
|---|---|
| 节点右键 →「端点 ▶」 | 加输入 / 加输出 / 改标签 / 删除 / **恢复默认** |
| 画布上拖端点 | 沿边滑动改 `at`（像拖拐点那样） |
| 双击端点标签 | 就地改文字（像双击连线标签） |

「恢复默认」要显眼 —— 用户把端点搞乱了得有条退路。

---

## 8. 迁移与兼容

| 情况 | 行为 |
|---|---|
| 节点没有 `ports` | 默认四向，和现在**完全一样** |
| 边没有 `sPort` / `tPort` | 落到默认端点 |
| **删掉一个还有边挂着的端点** | 那些边**回落到默认端点**，**不删边** |
| 老存档 | 零改动 —— 这三个字段全都是可选的 |

「删端点不删边」和现在「删节点」的策略一致：宁可留个需要用户处理的东西，也别静默销毁数据。

## 9. 建议分四期做

| 期 | 内容 | 能不能单独发 |
|---|---|---|
| **1** | 数据模型 + 渲染 + 命中 + 连线。**不动取值逻辑**，纯交互 | 能 —— 老行为完全不变 |
| **2** | 程序组输出端点绑定 + `{组名.端点名}` 取值 | 能 |
| **3** | 标签编辑 + 沿边拖动 | 能 |
| **4** | 面板 UI（增删改端点） | 能 |

第 1 期做完就应该能拉出多条线到同一个节点的不同端点，只是取值还是老逻辑。**先把交互跑通再看取值**，这样出问题时好定位。

## 10. 已知风险

### 10.1 多输出时的取值语义要定死

现在是「**每条路径各带各的值**」（每个 BFS 分支独立累加）。多输出端点之后，「同一条边到底用哪个输出端点的值」必须有明确规则。

**建议**：按端点分别求值，各走各的路径。和现有模型一致，不引入新的作用域概念。

**不要**做成「所有输出端点共享一个累加器」—— 那个坑踩过：`evalFromIn` 早期用共享累加器，导致分支互相污染。

### 10.2 折叠 / 导出 / 对齐 / 命中都要按新端点表重算

> 「导出时漏掉连到分组的边」这个 bug，我**犯了三次** ——
> `buildExportCanvas`、`drawGraphForExport`、`deserialize` 各写各的过滤条件。

所以这次**一开始就把 `exportPlan()` 那类「所有地方共用一份」的入口建好**，别再各写各的。

要检查的地方（动手时照着过一遍）：

- [ ] `exportPlan()` / 导出画布
- [ ] `computeHidden()`（折叠时端点算不算可见）
- [ ] 对齐 / 分布（端点影响 `nodeBox` 吗？不应该，但要确认）
- [ ] `hitPort` 的所有调用点
- [ ] 端点吸附面板（`endbox.js`）—— 现在按四向列，要改成按端点表列
- [ ] 「钉死锚点」的逻辑（`aSide` / `bSide`）和 `ports` 的关系要想清楚

### 10.3 `aSide` / `bSide` 和 `ports` 的关系

现在边有 `aSide` / `bSide` 记录「钉死在哪个方向」。加了端点之后，这两个字段要么：

- **(a)** 保留，作为「自动锚点」的方向提示；显式指定了 `sPort`/`tPort` 时以端点为准
- **(b)** 废弃，统一用端点表达

**建议 (a)** —— 老存档里的 `aSide`/`bSide` 是一大堆断言和用户文档在依赖的东西，废弃的迁移成本没必要承担。默认端点的 `side` 就从 `aSide`/`bSide` 推导。
